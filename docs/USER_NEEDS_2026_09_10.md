# 目标用户与下一步需求判断

日期：2026-09-10。范围：只读核对产品与代码，未调整功能或服务。

## 判断依据与限制

本次依据作者近期实际使用反馈、当前前后端代码和已有能力判断优先级。尚无代表性玩家访谈、用户构成统计或使用漏斗，因此这里是可验证的产品假设，不是需求调研结论。早期项目基线中的“缺少导入、对比、Agent”等描述不能直接作为当前缺口。

近期反馈集中在组合条件、组合外反例、实际循环差异、宏编辑、状态解释与测试服机制可信度。最明确的种子用户是研究循环、自己修改宏的苍云 PVE 进阶玩家和宏作者。另一类值得服务的是带着自己的配装和现成宏来检查适用性的普通玩家。招聘评审是作品成果的读者，不代替玩家需求。

共同任务是：确认当前输入确实代表自己的角色，得到能实际使用的宏，并在失败时知道该检查和修改哪里。

## 当前已有能力

- 装备多格式导入、宏预设、完整方案存档及横向对比已经存在。
- 写宏模式已有单技能/连续组合分析、负样本、独立草稿、真实运行、红绿对照和可见栏行定位。
- 宏蒸馏/优化流程已有分场景验证；延迟、初始怒气、时长与停手属于已有场景维度。接入新的写宏入口前须核对环境和对齐口径。
- Agent 已有时间轴诊断、候选比较和逐页宏卡片。增加另一个聊天框、导入器或优化器不是本次建议。
- 外部 JX3BOX 项目已有宏库和云端更新定位。这里的差异化更适合围绕个人配置适配、验证和解释，而不是再建一套宏分发系统。来源：[JX3BOX 宏库项目配置](https://github.com/JX3BOX/macro/blob/master/setting.json)。

## 优先级与可审查缺口

### 先收好现有写宏流程

1. **每栏的游戏用宏输出。** `frontend/macro-editor.js` 的计数和复制仍使用完整模拟文本：合计字数、包含 `#page`。编辑区隐藏页头并不等于复制输出已去掉它。`frontend/agent.js` 的宏卡片已实现本页正文复制与独立 128 字计数，可统一规则后接入写宏区；复杂多页需逐页保留优先级。
2. **统一不同入口的技能比较口径。** `frontend/macro-alignment.js` 保留阵云、月照、雁门独立身份；`backend/src/agent/macro_tuning.rs::counts` 仍无条件将月照和雁门合并到阵云。它影响候选评分中的次数差异判断，不能据此断言核心 DPS 计算错误。先统一版本感知的比较规则，再扩展“还原循环”的结论。

这两项范围小，能立即提升正在使用写宏模式的用户的完成率。

另有两项基础体验值得一并修正：主模拟在 `app.js` 中将非成功 HTTP 响应抛成空错误，再统一显示“后端未连接”，用户无法区分超时、配置错误与真实断连；循环编辑器自动保存只有一个 `jx3_autosave_loop_v1` 键，虽然恢复会检查版本/心法，但无法同时保留正式服和测试服各自最近的工作现场。写宏草稿已按账号/版本/心法隔离，主循环可沿用一致的产品规则。旧结果应标明所属配置，错误应给出对应的恢复动作。

### 下一项核心能力：解释首处技能分歧

用户问题：这里该放月照，实际没有放，我应该看哪条条件、改哪一行？

当前详情列出释放前状态和成功执行的宏行，尚不能回答某次没放的具体原因。`backend/src/macro_eval.rs` 已有 `MacroStepDebug` / 两阶段调试结构，但完整记录处于关闭状态，`main.rs` 也不发送整场调试数据；`macro_line_stats` 是整场累计，不能替代这个决策点的证据。

最小实现放在现有差异详情中：按需取得首处分歧附近有限决策记录，展示相关宏页、条件真假、技能可释放性和最终选中行。优先解释条件未满足、资源/冷却限制、前行优先和页内没有目标行。对没有决策证据或对齐不确定的情况明确显示无法确定，不从快照猜原因。

后续再将一项候选改动与完整原宏做同环境复跑，呈现关键漏放是否减少、是否引入新问题。自动修复不能仅优化一个局部片段；未经统一伤害窗口结算，不宣称精确 DPS 收益。

### 普通玩家的第一步：确认输入，并跑通可信基线

当前首页首先展示“循环蒸馏 / timeline”等工具概念；已有工作流向导，但缺少围绕“我的配装 + 我的宏”的短路径。

更具体的缺口是宏预设：`main.rs::macro_presets` 读取单一 `backend/macros/presets.json`；`app.js::initMacros` 在没有可用存档时回退到第一条预设。它不构成按版本与心法验证过的完整开箱方案。

建议每个受支持的版本×心法提供一份明确环境、已验证能跑通的入门方案；玩家导入配装后展示实际采用与仍沿用的配置，让玩家确认奇穴、秘籍、加速、延迟和团队环境。复用现有导入与模拟入口，以一次成功且可理解的首跑作为完成条件。

具体导入边界：`app.js::_importEquipmentFromJx3Box` 明确不应用 `Mount/TalentCode`，避免覆盖当前心法/奇穴，但成功提示未将“装备导入”与“整套角色配置导入”充分区分；在线库格式的小附魔匹配失败可能保留 `enhanceId=0`，该分支未增加对应告警。这不等于所有导入都静默失败：在线库缺失装备和未匹配大附魔已有告警，应该补齐遗漏项并统一呈现。

### 宏的适用范围与版本可信度

复用现有多场景模拟，让用户知道当前宏在哪些已测试的延迟、资源和时长条件下通过，在哪些条件下漏放或空转。结果应绑定宏文本、完整环境与规则版本，不使用笼统的“通用最优”。

测试服还需要在相关技能/方案处展示来源与待确认边界。部分未公布机制的沿用规则已经记录在 `docs/baselines/2026-09-08-cangsheng-test.md`，可将与当前技能有关的边界接到界面。公告来源、程序已实现和实测已验证应分别表达，不能合并成一个“已确认”标签。

## 建议实施顺序与验证方式

实施顺序：补齐每栏输出与统一比较规则 → 首处分歧解释 → 接入适用范围验证。普通玩家的首跑方案和导入摘要作为降低使用门槛的配套工作，不再增加一套独立大工作流。

错误分类和各版本自动保存属于现有工作流的基础修复，可与每栏输出一起安排，优先保护用户已经投入的编辑时间。

以下是建议的验收任务，不是已取得的用户指标：

- 让宏作者从一份有已知缺陷的宏开始，记录找到正确修改行、修改后通过验证所需时间与运行次数。
- 提供“漏一技能、条件边界、姿态页遮蔽、仅资源不同”等固定反例，检查诊断是否引用真实决策，是否把未知说成确定。
- 检查仅互换阵云和月照的候选，所有比较入口均能按当前版本识别技能差异。
- 玩家能分别复制盾宏和刀宏正文，准确看出哪一页超限，复制内容与界面显示一致。
- 首次用户从版本/心法选择或导入开始，在无需作者口头帮助的情况下完成首次模拟，并能说清结果采用了什么配置。

先用少量目标玩家观察这些任务的成功与失败，再决定是否扩大自动修复、教程或内容分发功能。
