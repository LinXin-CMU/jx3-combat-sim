# 宏蒸馏接入修复 v49

## 反馈与根因

反馈 run `run-1a076e5179e-3`，场景 `c5d9e9642e69de0da9ae54314e3b1fe650ef490032a428767dba765b412d19cc`。

原冻结轴 DPS 2,968,513.35。v48 初稿和调优终稿均为 26,446.73，300 秒附近只释放 6 次业火麟光。盾击上的 `rage>=5` 阻止初始 0 怒起手。算法实际测试过删掉该条件，恢复到 320 次盾击、451,992.19 DPS，但拒绝采用。

1. Agent 接入剪枝时把计数保护范围从旧前端的 `baseCounts.keys` 改成旧/新技能并集，把新恢复技能误认为超限漂移，阻止脱离死循环。cast-diff 同样不接受这一步，但这是旧算法的目标：新候选盾击过量，加权偏差从 363 增至 467。旧工作流依靠后续剪枝跨过这个中间状态。
2. 新接入把候选尝试次数均分到四个阶段，缓存命中也消耗份额，提前停止阶段。该轮只实际运行 50 个候选就标记额度耗尽。旧工作流每轮评估全部候选，用户再次点击会续调。
3. 条件微调还额外加了旧实现没有的“次数偏差不恶化”。旧前端注释与实现存在差异，本次按实现对齐。
4. 模型调用一次蒸馏后转向知识搜索与输入检查，没有调用 `compare_scenarios`，交付的是另外一份未测手写宏。报告中的“分段验证”缺少对应实验。

旧生成器与宏运行器未在本次修改。用户旧工作流保存的生成参数未取得，不能宣称完全复刻了用户当时的生成过程；这里验证的是同一反馈冻结轴、旧生成器默认参数与调优接入修复。

## 改动

- 对齐旧工作流剪枝与条件微调的接受逻辑。
- 去掉阶段均分额度；候选共用实际模拟缓存及额度。
- 工具内从选定候选连续执行工作流，直到无新接受版本或达到实际模拟/时间额度；保留循环去重。
- 默认算法额度 384，单次最大 512；Agent 单轮默认模拟额度 512，上限 1024。模型轮数、模型工具次数、API 输出额度未提高。保留 20 秒算法软时间检查和后续模拟预留。
- 工具新增目标计数、目标 DPS 比例与缺失技能表。Skill 引导模型基于调优后的候选定位差异、微调完整宏、实际对比；正常只交付一份选定宏。
- Prompt v49，业务 Skill `macro-distillation/v2`。中间候选仍只进入后台调试。
