# 精确宏第二阶段：批量压缩与验证开销

发布日期：2026-09-30；界面版本：`v2.1.0-20260930.17`。

## 问题与改动

旧压缩器通常在找到一次可接受的修改后，立即重新构造整份样本和候选。旧版已有局部多行合并，但主循环以逐条删除、逐条删条件为主，因此长宏要重复很多轮构造和验证。

这次只改变第二阶段搜索效率。第一阶段仍先提取可复现的宏；第二阶段继续使用原目标、完整场景、原终点与时间容差，不需要参考宏 B。

1. 先在已认证轨迹上规划一批兼容修改，包括删除候选行、删条件、转换命令、合并同动作规则及替换整组条件。样本检查遵循首个满足条件且可执行动作的选择关系；样本兼容只能作为搜索提示。
2. 一次将整批修改交给真实宏解析器和执行器回放。整批失败时，按稳定的原始行 ID 二分拆分，并逐步保留已经独立验证通过的子批。单批最多检查 12 个失败组，之后继续其他搜索邻域；这不是总运行时间限制。
3. 缓存条件真值位集上的命中结果、条件长度和短条件特征；同一份样本只构造一次，候选排序只渲染一次。整批验证成功后才重建下一份样本。
4. 失败候选的初步回放只收集一个合法观察原子的真值，避免为约 1800 个诊断原子逐状态求值和输出。候选宏自身的条件、Buff 阈值和原生时间推进完全保留。初步通过后再从零执行一次独立完整回放，使用全部观察原子，生成本地证据及下一轮样本。
5. 压缩失败轨迹不作为通用约束追加；不同候选路径的状态不会混成一份无条件标签。单行修改、局部 SAT、有限宽度优先级搜索仍作为后续搜索手段。

只有更短且取得完整回放认证的宏才能替换最佳宏。批量修改失败不会覆盖已有最佳宏。未被选中的规则仍可能影响唤醒时机，不能凭样本计数直接删掉；针对这种情况增加了拆批保留必要等待规则的回归。

## 同场景实测

使用同一台机器串行测量，均不启用性能分析器。固定正式服暗影千机 / 分山劲场景、325 次主动施放，初始宏 95 行、3110 个 UTF-16 字符，观察原子 1793 个。时间验收容差为 0.0625 秒，终点为 299.45750010000023 秒。初始化和起始宏认证不计入压缩时间；压缩时间包含候选构造、模拟、进程通信、独立完整认证和本地记录。

新版第一批一次修改 26 行，即从 3110 压到 2428 字符。这一共同长度里程碑在本案例约快 35 倍；不能将这个倍数推断为所有循环的总耗时加速比。45 秒是本次对照实验的观察窗口，产品没有新增最长运行时间。

本案例按 `skills_and_time` 验收。两版均不要求每个隐藏状态相同；隐藏状态诊断的匹配前缀分别为 46 和 22，这不等同于技能或时间分歧。

## 必要验证

- 第二阶段压缩契约：6 项通过，包括一次删除 39 行，以及拆批保留影响唤醒时机的规则。
- 原有求解契约：29 项通过。
- 原生回放观察精简验证：通过宏、失败宏、Buff 阈值唤醒、引导技能，分别比较完整回放与首次分歧提前结束；精简/完整观察目录的比较结果、主动轨迹指纹和决策时间一致。
- 隔离 worker 自动两阶段及界面验证：23 次主动施放全部复现，229 → 178 字符，最大时间误差 0；暂停计时冻结、继续、压缩中停止、首次候选直接通过时的阶段切换，以及最佳宏保留全部通过。

验证入口位于 `backend/tests/macro_exact/compression_test.py`、`screening_test.py`、`compression_benchmark.py`、`stage2_ui_test.js`。同场景对照可将 `compression_benchmark.py --module` 指向旧压缩器，新版额外传入 `--screening`。`--seconds` 仅是该测试脚本的观察窗口。

## 使用与边界

本次没有修改 Rust 模拟器或后端协议，不需要重启既有 worker。新任务会加载新版脚本；已经进入压缩阶段的任务继续使用启动时的代码。界面仍逐次显示待测试宏、已验证最佳宏和差异，完整证据只留后端。

搜索仍是有限邻域的启发式压缩，不保证全局最短宏，也不将邻域耗尽解释为所有合法宏无解。新的批处理和缓存没有改变这个边界。
